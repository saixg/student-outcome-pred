EduPredict AI --- Three-Step Implementation Plan

1. Project Goal

Build a small, complete Machine Learning project that predicts one of
the student outcome classes in the selected UCI dataset:

Dropout

Enrolled

Graduate

The system is a decision-support prototype, not a definitive
judgment about a student. Its purpose is to demonstrate a reproducible
ML workflow and a working interface.

2. Build Strategy

Build the project in exactly three implementation steps:

Data + ML pipeline --- understand the dataset, prepare it, train
models, evaluate them, and save the best complete pipeline.

Streamlit application --- create a working interface that loads
the saved pipeline and displays predictions and verified model
results.

Testing + submission package --- verify the end-to-end flow,
document limitations, and produce the required Lean Canvas, Concept
Note, and PowerPoint.

Do not build a database, separate API, authentication, deep learning
model, cloud deployment, or extra dashboard pages for this mini-project
unless a real requirement emerges.

3. Technology Stack

Python

pandas and NumPy

scikit-learn

Matplotlib (Seaborn optional)

Jupyter Notebook (optional, for exploration)

Streamlit

Joblib

Git (recommended)

4. Step 1 --- Data Understanding and ML Pipeline

Objective

Produce a trained, evaluated, reproducible model pipeline. Do not begin
UI work until this step passes its acceptance checks.

Tasks

Inspect the existing repository before creating or modifying files.

Download or locate the official dataset; preserve the raw file
unchanged.

Inspect the dataset shape, column names, data types, target column,
class distribution, missing values, and duplicates.

Read the dataset's feature descriptions and decide what information
is available at the intended prediction time.

Define the prediction target and explicitly document any excluded
features. Avoid target leakage. If using later-semester
academic-performance features, describe the task as student outcome
prediction rather than claiming it is an early-warning model.

Create a reproducible train/test split, preferably stratified for
the multiclass target.

Build preprocessing inside a scikit-learn Pipeline/ColumnTransformer
where appropriate. Fit learned preprocessing only on training data.

Train and compare three classifiers:

Logistic Regression (baseline)

Decision Tree

Random Forest

Evaluate each model on the same held-out test set using accuracy,
macro F1, weighted F1, per-class precision/recall/F1, and a
confusion matrix. Do not rely on accuracy alone.

Select a model using measured results and the project's purpose; do
not assume Random Forest wins.

Save the complete preprocessing + model pipeline with Joblib.

Save the model comparison results, confusion matrix, and useful
data-analysis charts.

Record the random seed, split strategy, target definition, feature
choices, and package versions.

Suggested outputs

data/raw/ --- unchanged source dataset

data/processed/ --- only if a processed export is genuinely needed

notebooks/01_data_understanding.ipynb --- optional exploration
notebook

src/train.py --- reproducible training/evaluation script

models/best_model.joblib --- saved full pipeline

outputs/model_comparison.csv

outputs/confusion_matrix.png

outputs/outcome_distribution.png

outputs/metrics.json

requirements.txt

Keep the structure lean. If a notebook-only workflow is simpler for the
first pass, it is acceptable, but the final training procedure must be
reproducible.

Acceptance checks

Dataset source and target column are documented.

No preprocessing is fitted on the test set.

All compared models use the same split.

Results are generated by running the code; no invented metrics.

The saved pipeline reloads successfully and predicts on a valid
sample.

Any early-warning claim is consistent with the features available at
prediction time.

5. Step 2 --- Streamlit Application

Objective

Build a small, reliable app around the saved model. The app must not
retrain the model on startup.

Required interface

Keep it to one Streamlit app with three clearly separated sections or
tabs:

Overview

Project purpose and disclaimer

Dataset/target summary

Actual evaluation metrics loaded from saved results

Outcome distribution chart, if available

Predict

Input fields for the features required by the saved pipeline

Input validation and sensible defaults based on the dataset

Predict button

Predicted class, displayed clearly

Optional class probabilities only if the selected model supports
predict_proba; label them as model estimates, not certainty

Reminder that predictions require human review

Model Performance

Actual comparison table

Confusion matrix

Per-class metrics where available

Short limitations statement

Implementation requirements

Load models/best_model.joblib and saved metrics/results.

Ensure input column names and data types match training-time
expectations.

Never manually recreate preprocessing in the app if the saved
pipeline already handles it.

Show a clear error if the model or results files are missing; do not
silently fabricate fallback output.

Keep the interface usable on a normal laptop screen.

Use only features that the trained pipeline expects.

Do not add a database, login system, or separate backend for this
mini-project.

Acceptance checks

streamlit run app.py starts successfully.

A valid input produces a prediction without retraining.

The app's metrics match the saved evaluation results.

Missing model files produce a helpful error rather than fake output.

Prediction output includes a non-deterministic-outcome disclaimer.

At least three valid input cases are tested and recorded.

6. Step 3 --- Verification and Final Deliverables

Objective

Verify the whole project, then prepare submission materials using only
confirmed implementation details and measured results.

Testing checklist

Install dependencies in a clean virtual environment.

Run the training pipeline from documented instructions.

Confirm the model and metrics artifacts are generated.

Launch the Streamlit app.

Test representative valid inputs and one invalid/missing-input case.

Check that displayed metrics match the saved files.

Check that screenshots do not contain placeholder or fabricated
results.

Verify that the README instructions work from a fresh setup.

Review the target definition, data leakage risk, class imbalance,
privacy, fairness, and generalization limitations.

Required submission documents

Prepare these three deliverables, as listed in the project brief:

Lean Canvas PDF --- problem, users, solution, value proposition,
alternatives, metrics, channels, costs, and possible revenue model.

Concept Note --- problem, motivation, solution, objectives,
dataset, methodology, actual results, limitations, impact, and
future scope.

PowerPoint presentation --- approximately 10--12 slides covering
the problem, dataset, method, models, actual results, app
screenshots, limitations, and conclusion.

Also provide: - README.md - requirements.txt - Source code - Saved
model pipeline if allowed by submission rules - Screenshots of the
working app - Actual model results and charts

Final acceptance checks

The app runs from documented instructions.

The training/evaluation method is reproducible.

All metrics in the app and documents match actual outputs.

No fabricated results or unsupported claims appear.

The dataset is cited.

The model is described as decision support, not as a guaranteed
judgment.

All three documents open correctly.

7. How to Work with Antigravity + Gemini 3.8 Flash

Use the IDE agent to implement one step at a time. Do not ask it to
build the entire project in one giant prompt.

For each step: 1. Give the agent only the current step and this plan. 2.
Ask it to inspect the repository before editing. 3. Require a short
implementation plan before broad changes. 4. Ask it to implement, run
available checks, and report exact files changed. 5. Require it to
distinguish implemented and verified, implemented but not
verified, and not implemented. 6. Review the output and run the
app/tests before moving to the next step.

Agent guardrails

Do not invent dataset columns, metrics, screenshots, test results,
or completed features.

Do not silently change the target label or feature set.

Do not use test data to fit preprocessing or choose parameters.

Do not hard-code example predictions or evaluation scores.

Do not create extra architecture or dependencies without explaining
why they are needed.

Preserve working code and make focused changes.

If an assumption blocks implementation, inspect the source data or
ask for clarification instead of guessing.

At the end of each step, provide run commands, test results, known
limitations, and the next step's prerequisites.

8. Recommended Execution Order

First: complete Step 1 and verify that the saved pipeline predicts
correctly.

Second: complete Step 2 and verify the app uses that saved pipeline.

Third: complete Step 3 and finalize the documents using real
outputs.

Do not spend time polishing the UI or writing final presentation claims
before the ML pipeline is verified.
